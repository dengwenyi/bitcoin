# C++ 全节点最小化裁剪可行性分析

## 1. 结论

可以把当前 Bitcoin Core 31.1 C++ 工程精简为只运行全节点所需的版本，但应分三个层次处理：

1. **最小构建**：不删除源码，只让 CMake 生成一个无钱包、无 GUI、无工具和无测试的 `bitcoind`。风险最低，可以立即做。
2. **最小运行配置**：关闭可选索引、REST、UPnP/NAT-PMP、钱包、ZMQ 等运行能力。仍不改共识代码。
3. **物理源码裁剪**：拆分 `bitcoin_node`、`bitcoin_common` 后，才删除 RPC、索引、挖矿、PSBT、额外网络传输等源码。可以做，但风险和维护成本明显更高。

推荐目标不是“文件数量最少”，而是：

> 只产出一个能够独立同步、完整验证、持久化区块和 UTXO、处理重组并参与 P2P 网络的无钱包 `bitcoind`，同时保留验证与抗攻击所需的全部代码和测试来源。

## 2. 必须先定义“全节点”

本文把目标分成两种：

### 2.1 标准验证与中继全节点

必须保留：

- P2P 连接、地址管理和区块同步；
- 区块头、PoW、交易和 Script 验证；
- block index、区块文件、undo 和 chainstate；
- UTXO 缓存、最佳链选择和链重组；
- mempool、交易接收和中继；
- 对等节点限流、超时和反 DoS；
- 配置、日志、优雅退出及最低限度的运维接口。

这是本文推荐的“最小全节点”。

### 2.2 仅区块验证节点

如果明确接受 `-blocksonly=1`，可以不接收普通 peer 的交易，也不主动广播交易。

但是当前代码在 [src/init.cpp](../src/init.cpp) 第 1321–1322 行仍会创建 `CTxMemPool`，并把它交给 chainstate 和 peer manager。也就是说：

- 运行时启用 `-blocksonly` 很容易；
- 从源码中彻底删除 mempool 并不容易；
- 删除 mempool 会影响 reorg 后交易处理、compact block、RPC、矿工模板和 PeerManager 状态。

首期不建议物理删除 mempool。

## 3. 当前构建结构说明

当前 [src/CMakeLists.txt](../src/CMakeLists.txt) 中：

```text
bitcoind
  └─ bitcoin_node
       ├─ bitcoin_common
       │    └─ bitcoin_consensus
       │         └─ bitcoin_crypto + secp256k1
       ├─ bitcoin_util
       ├─ LevelDB / CRC32C
       ├─ libevent
       └─ minisketch
```

钱包启用时，`bitcoind` 还会链接 `bitcoin_wallet`；关闭 `ENABLE_WALLET` 后则使用 `dummywallet.cpp`。

### 3.1 `bitcoin_consensus`

该库包括：

- 交易和区块基础类型；
- Merkle；
- Script interpreter；
- 哈希、uint256 和椭圆曲线验证依赖。

这是不能裁掉的核心。

### 3.2 `bitcoin_common`

该库同时包括：

- chain params、PoW、coins、协议和策略等必需代码；
- 地址、配置、调度等运行基础；
- descriptor、sign、PSBT、raw transaction utility 等非最小节点必需代码。

因此关闭钱包后，`bitcoin_common` 仍不是物理意义上的最小库。要继续减小源码和二进制边界，需要先拆分它。

### 3.3 `bitcoin_node`

`bitcoin_node` 当前是最大的裁剪障碍。它在同一个静态库中同时编译：

- P2P、区块同步、验证、chainstate、mempool；
- HTTP、RPC、REST；
- txindex、blockfilterindex、coinstatsindex、txospenderindex；
- mining、mini_miner、PSBT；
- I2P、Tor control、端口映射；
- ZMQ 条件集成及其他节点服务。

所以“关闭运行参数”不等于“源码没有被编译”。如果要求物理最小化，需要把这个目标继续拆库。

## 4. 第一阶段：不改源码的最小构建

这是最安全、最值得先执行的方案。

### 4.1 保留的产物

- `bitcoind.exe`

### 4.2 关闭的产物与功能

- `bitcoin.exe` 聚合启动器；
- `bitcoin-cli.exe`；
- `bitcoin-qt.exe`；
- `bitcoin-tx.exe`；
- `bitcoin-util.exe`；
- `bitcoin-wallet.exe`；
- 实验性 `bitcoin-chainstate` 和独立 kernel library；
- 钱包、外部签名器、ZMQ、IPC、QR、GUI；
- 单元测试、GUI 测试、benchmark 和 fuzz 可执行文件；
- 安装 man pages。


该配置仍需要基础依赖：

- Boost headers；
- libevent；
- LevelDB/CRC32C；
- secp256k1；
- minisketch；

其中一部分是 P2P、chainstate 或现有 `bitcoin_node` 链接闭包的组成部分，不能仅凭“名字看起来可选”删除。

## 5. 第二阶段：运行时最小化

不修改共识代码的前提下，建议：

- `-disablewallet=1`：构建时已关闭钱包时只是重复保护；
- 不启用 `-txindex`；
- 不启用 `-blockfilterindex`；
- 不启用 `-coinstatsindex`；
- 不启用 `-txospenderindex`；
- `-rest=0`；
- 不启用 ZMQ；
- 按部署环境决定是否关闭 UPnP/NAT-PMP；
- 如果只需要区块验证，使用 `-blocksonly=1`；
- 如果仍希望作为标准交易中继节点，不使用 `-blocksonly`。

可选索引在 [src/init.cpp](../src/init.cpp) 第 1905 行以后只在参数启用时实例化；不启用它们不会影响主链有效性判断。

### RPC 是否保留

从比特币共识角度，RPC 不是必需的。

但从可运维全节点角度，建议第一阶段保留 HTTP/RPC，至少需要：

- 查询同步状态；
- 查询网络状态；
- 健康检查；
- 优雅停止；
- 诊断 chainstate 和 peer 问题。

当前 [src/init.cpp](../src/init.cpp) 会统一注册 Core RPC 并启动 HTTP/RPC。要物理删除 RPC，必须同时修改初始化、命令注册、接口和若干 node helper，收益通常小于维护成本。

## 6. 第三阶段：物理源码裁剪

物理裁剪不应直接从仓库删除目录，而应先创建清晰的新目标，例如：

```text
bitcoin_consensus       现有共识和 Script
bitcoin_chainstate      UTXO、block index、storage、validation
bitcoin_p2p             net、PeerManager、headers/block download
bitcoin_mempool         可选交易接收和中继
bitcoin_node_control    init、配置、日志、最小 RPC
bitcoind_minimal        最终可执行文件
```

只有链接闭包和测试通过后，才能判断哪些源码确实不再被引用。

### 6.1 可以优先剥离的代码

| 类别 | 候选源码 | 风险 |
|---|---|---:|
| GUI | `src/qt/` | 低，已有构建开关 |
| 钱包 | `src/wallet/` | 低，已有构建开关 |
| ZMQ | `src/zmq/` | 低，已有构建开关 |
| IPC | `src/ipc/` | 低，已有构建开关 |
| 独立工具 | `bitcoin-cli.cpp`、`bitcoin-tx.cpp`、`bitcoin-util.cpp`、`bitcoin-wallet.cpp` | 低，已有构建开关 |
| benchmark/fuzz 产物 | `src/bench/`、fuzz executable | 低，但测试源码必须保留在开发仓库 |
| REST | `rest.cpp` | 中，需拆 HTTP/RPC 注册依赖 |
| 可选索引 | `src/index/*` | 中，需移除参数、RPC 和全局生命周期引用 |
| 挖矿模板 | `node/miner.cpp`、`node/mini_miner.cpp`、`rpc/mining.cpp` | 中，需检查 fee estimator、mempool 与 RPC 引用 |
| PSBT/签名辅助 | `node/psbt.cpp`、`psbt.cpp`、descriptor/sign 相关 | 中高，当前混在 common/node 中 |
| I2P/Tor/端口映射 | `i2p.cpp`、`torcontrol.cpp`、`mapport.cpp` | 中，删除后只支持明确保留的传输路径 |
| 全量 RPC | `rpc/*.cpp`、`httprpc.cpp`、`httpserver.cpp` | 高，初始化和运维能力耦合较深 |

### 6.2 暂时不能删的核心

- `primitives/`、`consensus/`、`script/interpreter*`；
- `crypto/`、`secp256k1/`、hash、uint256、arith_uint256；
- `pow.cpp`、chain params、versionbits/deployment status；
- `validation.*`、`coins.*`、`txdb.*`；
- block storage、flatfile、undo、block index；
- `net.*`、`net_processing.*`、headers sync、block encodings；
- addrman/addrdb 及必要 peer 管理；
- chainstate manager、cache 和启动恢复；
- LevelDB、CRC32C、libevent；
- 对应的日志、参数、线程和中断基础设施。

### 6.3 建议保留而不是追求极限删除

- ban/discouragement 和反 DoS 代码；
- compact block；
- headers presync/minimum-chain-work 防护；
- embedded ASMap；
- pruning 与 reindex；
- 最小 RPC；
- mempool 与交易中继；
- 测试、fuzz 和功能测试源码。

这些模块有些不直接决定区块共识，但决定节点能否安全、可恢复地长期运行。删除它们会得到“能同步的实验程序”，不一定是合格全节点。

## 7. 为什么不能按目录直接删除

### 7.1 库边界还不等于职责边界

[doc/design/libraries.md](../doc/design/libraries.md) 明确显示 `bitcoin_node` 同时承担 P2P 与 RPC；验证代码也仍在逐步向 kernel 边界移动。

当前源码中：

- `bitcoin_common` 包含共识依赖和签名/PSBT 辅助；
- `bitcoin_node` 包含验证核心和大量可选服务；
- `init.cpp` 同时装配 P2P、chainstate、mempool、RPC、索引和可选模块。

所以“删除 `rpc/`”可能导致 node target 无法链接；“删除 mempool”会影响 reorg 和 PeerManager；“删除 miner”也可能通过 RPC 或 fee estimator 留下引用。

### 7.2 静态链接器裁掉代码不等于源码解耦

Release 链接时，部分未引用函数可能不会进入最终二进制，但对应 `.cpp` 仍会编译。需要分别衡量：

- 仓库源码体积；
- 编译时间；
- 最终二进制体积；
- 运行时内存和攻击面。

四个指标不能用同一种删除方法解决。

### 7.3 删除测试不是有效精简

测试不会进入生产 `bitcoind.exe`。删除测试源码不会降低运行时攻击面，却会失去证明裁剪没有破坏共识和恢复行为的能力。

生产构建可以不生成测试 executable，但开发仓库必须保留测试。

## 8. 建议的实施方案

### 阶段 A：最小构建基线

1. 新建独立构建目录 `build-node-minimal-vs2022`；
2. 使用第 4 节的 CMake 配置；
3. 只构建 `bitcoind` Release；
4. 记录 exe、DLL、依赖、构建时间和磁盘占用；
5. 完成启动、停止、RPC、regtest 和短链同步测试。

该阶段不修改源码，适合先验证真正节省了多少。

### 阶段 B：建立模块使用证据

1. 采集链接 map 和符号；
2. 统计各 object 是否进入最终二进制；
3. 运行覆盖率，观察 IBD、稳态同步、重组和关闭流程实际执行模块；
4. 把候选模块分为“未链接”“链接但未运行”“正常路径运行”“异常/攻击路径运行”。

不能因为正常同步覆盖不到某段代码就删除它；反 DoS 和恢复代码往往只在异常路径执行。

### 阶段 C：拆目标，不删历史

1. 从 `bitcoin_node` 抽出 chainstate/validation；
2. 抽出 P2P；
3. 将 RPC、索引、mining 变成显式可选 target；
4. 让现有完整 `bitcoind` 与新的 minimal target 同时存在；
5. 每次只移动一类源码并执行全量测试。

### 阶段 D：验收后决定是否删除

只有 minimal target 独立稳定后，才决定是否从定制分支物理删除不用的源码。更推荐保留上游源码、只维护独立 CMake target，因为这样更容易跟进 Bitcoin Core 安全更新。

## 9. 必须通过的验收

### 构建验收

- 配置摘要中只启用 `bitcoind`；
- 不查找 Qt、SQLite、ZeroMQ、Boost.Test；
- 最终产物中不存在 wallet、GUI、IPC、ZMQ 符号和运行依赖；
- VS2022 Release/Debug 均可生成和链接。

### 共识验收

- 从创世块同步并完整验证；
- 与未裁剪 Core 31.1 得到相同 active tip 和 UTXO commitment；
- 无效区块、Script、PoW、难度和激活边界结果一致；
- 一块、浅层和深层重组结果一致。

### 存储与恢复验收

- 正常重启恢复；
- reindex、prune 和数据库校验可用；
- block/undo/chainstate 写入中断后可恢复或明确失败；
- 磁盘满不会被误判为区块共识无效。

### P2P 与运行验收

- headers、blocks 和 compact blocks 同步正常；
- peer 超时、恶意消息和资源限流仍有效；
- 断线重连和 stale tip 恢复正常；
- 保留可观测日志和优雅停止手段。

## 10. 最终建议

可以做，而且第一阶段不需要改动共识源码。

推荐顺序是：

```text
最小 CMake 构建
    -> 测量真实收益
    -> 建立符号/覆盖率证据
    -> 拆 bitcoin_node / bitcoin_common
    -> 每次裁一类可选模块
    -> 全量共识、P2P、重组和恢复验收
```

不推荐：

```text
复制源码 -> 直接删除看起来无关的目录 -> 修到能编译 -> 当作最小全节点
```

“能编译”和“能同步正常主链”都不足以证明裁剪正确；最终标准必须是验证结果、状态转换、P2P 防护和异常恢复均未退化。
